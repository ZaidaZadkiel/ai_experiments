# 50. Viewer UI

What the MVP Viewer page looks like and holds: every UI detail known so far, and the suggested answers to what is still open.

Each item is marked:
- **[Decided]** decided by the user for the MVP.
- **[Accepted]** a suggestion the user accepted.
- **[Known]** follows from a decision or an accepted MVP requirement, with its source.
- **[Suggested]** not yet accepted; a starting answer so the build doesn't have to invent one.

The backend, the data rules and the checks stay in `05_viewer.md`; this file covers only what the user sees and does. Where the two differ, `05_viewer.md` and the working files win, and this file is corrected.

## 1. Starting the page

- **UI-01** **[Known]** the backend is started by hand from a shell, `zaansouvi-view [--port <n>]`, and prints the URL to open, with its token, on standard output; it doesn't open the browser itself, and runs until stopped by hand (`VIEW-07`).
- **UI-02** **[Suggested]** the printed message, one line per fact, plain text:

  ```
  ZaAnSouVi Viewer 0.1.0
  Open in your browser: http://127.0.0.1:4310/?token=<token>
  Stop with Ctrl + C.
  ```

  A port already in use prints `Port 4310 is in use. Start with --port <n> to use another.` and exits (`VIEW-07`).
- **UI-03** **[Suggested]** opening the page without the token, or with a wrong one, shows only a short text: "This page needs the link printed by zaansouvi-view." Nothing else is served (`FND-60`, item 3).

## 2. Page layout

- **UI-10** **[Known]** the page has a **header** linking to the pages, a **graph area**, a **details drawer** and a **status bar**, and shows where the user is in the levels, for example as a breadcrumb (`viewer.md`, sections 4.8 and 4.10).
- **UI-11** **[Suggested]** The arrangement, for a desktop browser window:

  ```
  +----------------------------------------------------------------------------------+
  | ZaAnSouVi  [Viewer]  Config  Status  Runs  | Source: [test-source v] [Run] [Dry run] |
  +----------------------------------------------------------------------------------+
  | test-source > main.ts > run                                 | Details|Tools|Problems|Legend |
  | +----------------------------------------------------------+ |                     |
  | |                                                          | |  (drawer, about     |
  | |                       graph area                         | |   360 px wide)      |
  | |                                                          | |                     |
  | +----------------------------------------------------------+ |                     |
  +----------------------------------------------------------------------------------+
  | 14:02:31  Dry run finished: 5 of 5 go, 0 errors                          [^ 12]  |
  +----------------------------------------------------------------------------------+
  | /home/.../test-source | run 2026-11-09 01:36, latest | 0 invalid | 2 unresolved   |
  +----------------------------------------------------------------------------------+
  ```

  The line above the status bar is the activity line (`UI-65`), collapsed to the latest entry; `[^]` expands it; the count "shown / logged" stands at the start of its controls (`UI-73`).

- **UI-12** **[Suggested]** the drawer sits on the right; the graph area takes the rest. The breadcrumb sits above the graph, inside the graph column. Its width is set by a handle (`UI-88`), and a small button on the handle collapses it to a narrow strip and opens it again, in place of the tab bar's button.
- **UI-88** **[Decided]** **The drawer's width is set by dragging a handle** (decided by the user, 2026-11-10). A handle along the drawer's left edge, which the pointer drags.
  - **The show/hide button (⇆) is removed** from the tab bar: the drawer is made narrower with the handle instead of collapsed. This also frees the room the five tabs need (`UI-51`), which had pushed ⇆ past the drawer's edge.
  - **While dragging, the drawer is drawn over the Graph**, at the width the pointer sets; the Graph is not laid out or resized during the drag. **The Graph is redrawn once, when the mouse button is released**: the graph area takes its new width, and the Graph is resized to it (`cy.resize()`), its nodes keeping their places.
  - **Collapsing: a small ‹ / › button on the handle** (decided by the user, 2026-11-10, of four options: dragging past the smallest width to snap shut, a double-click, this button, no collapsing). ‹ collapses the drawer to a narrow strip holding the handle and the button; › opens it again at the width it had. Each is one redraw of the Graph, as on a release.
  - **No keyboard control** for the handle, for now.
  - **Limits and details** (suggestions accepted by the user, 2026-11-10): the smallest width **360 px**, enough for the five tabs with Problems' count; the largest, **the window's width less 400 px**, so the Graph stays usable; the width **remembered in this browser** (`localStorage`), surviving a reload, kept for the page only when storage is blocked; **a double-click on the handle restores 380 px**; while shrinking, the strip the drawer leaves is plain background until the release; **no handle below 900 px**, where the drawer sits under the Graph. While collapsed, the handle doesn't drag.
  - *(As built, `FND-118`: the drawer's handle in `ui/src/main.ts`, `.drawer-handle`, `.drawer-toggle` and `aside.drawer.overlay` in `ui/static/style.css`, the grid's column from `--drawer-w`. Checked in headless Firefox, `tests/viewer/browse/drawer.json`.)*
- **UI-13** **[Suggested]** one page only. The header shows **Viewer** as the current page; Config, Status and Runs are shown greyed out with the note "not in the MVP" on hover, so the header already has the shape `viewer.md`, section 4.10, describes. The MVP has no config manager (`ARCH-11`).
- **UI-15** **[Decided]** **Display controls in the bottom right corner** (a guideline; recorded in `viewer.md`, section 4.8): buttons that change how the content is shown align to the bottom right of what they act on, as a column with the part that changes most (a count, a readout) kept in the corner and the controls that affect the visualization above it, so that what needs the most attention, and the controls that change what is visible, each stay in the same place in most cases, or as a row ordered with the items that change most first (`{count} [action 1] [action 2] [change display]`). Exception: a layout whose buttons are better placed otherwise for their function, such as run configurations. Followed by the zoom controls (`UI-46`), the This view / All toggle in Problems (`UI-57`) and the activity line (`UI-73`).
- **UI-14** **[Suggested]** a light and a dark theme following the system setting; nothing to configure.

## 3. Header

- **UI-20** **[Known]** the user picks the examined source: the page lists the sources the Viewer has cached and takes a new source root; picking one shows its cached graph at once, marked with its run's time (`VIEW-08`).
- **UI-21** **[Suggested]** a drop-down **Source** with each cached source by its folder name, the full path on hover, and its last run's time; its last item, **Add a source...**, opens a small form with one text field (the absolute path of the source root) and **Add**. A new source has no graph until it is run; the graph area then says so and points to **Run**.
- **UI-22** **[Known]** two buttons, **Run** and **Dry run** (`VIEW-32`). Run starts a real run on the source shown; it is the user's way to reload the graph (`VIEW-33`).
- **UI-23** **[Known]** one run at a time; a second request is refused, with the Runner's message (`VIEW-05`). **[Suggested]** both buttons are disabled while a run is in progress, with "A run is in progress" on hover; switching sources is disabled too.

### 4.1 What each level shows for the test source

The Viewer's event names differ from the Runner's (`run_result`, not `run_finished`), so the two programs' events are never confused.
  - **Only one backend uses it**: no locking and no sharing between backends are needed, and the file may be deleted and recreated at any time without breaking anything. **[Suggested]** the backend opens the file, appends one entry and closes it again for every entry, so a file deleted while it runs is simply created again by the next entry.

This can't be undone."). It touches nothing else: not the Runner's or the tools' logs, not the cached graphs (`VIEW-09`).

Runs started outside the Viewer, from the command line, don't appear, since the Viewer doesn't see them happen; a later load of their result does.
