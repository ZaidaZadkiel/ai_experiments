Each finding has an ID (`FND-nn`) so it can be referred to when it is fixed. When one is fixed, strike it through and say where the fix is recorded.

## 1. Gaps to close before coding

- ~~**FND-01 No rule links a data name to a part of an output file.**~~ Resolved for the MVP: the Runner matches keys to data according to each tool's `--info` (`jsonKey`, `fields`), every key name has one agreed meaning, and a reference JSON schema is built alongside (`DATA-18` to `DATA-20`, decided by the user on 2026-11-07). Still to fix in wording: `DATA-08` gives `files` the shape `"array of M1 outputs"`, which names a tool; `RUN-19` already builds it from the data name. Original finding: M1's file holds `symbols`, `references` and `diagnostics`, but its `--info` describes `code.symbol` and `code.reference`. ## 2. Smaller gaps

- **FND-09 `range` is ambiguous.** "Of the whole declaration; for a function, its full body." The parser shows the bodies start at 3:46, 5:45 and 4:22, after the parameters. If `range` meant only the body, `value` (3:23) would land in the file scope, against the expected table. It must mean the whole declaration, from `export` or `function` to the closing brace. That range also contains the function's own name, so the self-exclusion rule in `TOOL-31` is required.
- **FND-10 Call versus read.** `TOOL-14` should say only a bare-name callee is a `call`. In `Math.round(...)` and `console.log(...)` the callee is a property access, so `Math` and `console` are reads, as the expected table already has them.
- **FND-11 The file scope has no location.** M3 reads no files, so it can't know where a file ends (7:1, 9:1 and 13:1 for the test files). Either the file scope has no location, or the Runner passes file lengths.
- **FND-12 Scope IDs start where?** `DATA-03` says "at the start of the function". The parser gives the declaration start (3:1, including `export`), not the `function` keyword (3:8). Pick one; the inferred IDs below use the declaration start.
- **FND-13 Dry-run no-go on an invocation error.** Does the tool print a no-go JSON line, or only write to standard error and exit 2 (`toolset.md`, section 4.5: invocation errors go to the caller on standard error)? The Runner must handle a missing last line with exit 2.
- **FND-14 Tool options incomplete.** `TOOL-02` mentions command-line parameter arguments but defines none. `--help`, `--version` and the common options (source root, output root and so on), [Decided] in `toolset.md`, section 4.1, are missing without being marked as an MVP cut. If there are no per-parameter arguments, `TS-30` can't arise in the MVP; say so.
- **FND-15 Syntax errors (`TOOL-10`).** Checked: `parseDiagnostics` is not in TypeScript 5.6.3's public `typescript.d.ts`. `ts.createSourceFile` alone doesn't expose syntax errors through the public API; use `program.getSyntacticDiagnostics(sourceFile)`. B7 depends on this.
- **FND-16 Viewer server security.** Missing from `05_viewer.md`, all [Proposed] in `security.md`: the startup token and origin check (section 7); `/api/source` limited to files in `project_files` (section 7: reads only inside the examined project); Cytoscape bundled locally rather than loaded from the internet (section 8).
- **FND-17 Ctrl + wheel** is [Decided] in `viewer.md`, section 4.9, but cut in `VIEW-20`. Mark it explicitly as an MVP scope cut (`MVP_scope.md`, section 5, proposes following section 4.9).
- ~~**FND-18 M3 departs from `MVP_scope.md`.**~~ Resolved on 2026-11-08: `MVP-4` decided, option C with C1 (`FND-55`): M3 keeps lexical scope from symbols only, each scope names its `owner`, and the Viewer shows "the symbols it is used with". ## 9. Feasibility checks

Checks of what the design allows, written on 2026-11-07. They change no decision.

- **FND-35 M2 in plain C.** Feasible, with no hard limits, but **not within the MVP**: `MVP_scope.md`, section 2 [Decided], says the MVP's tools are TypeScript, and that stands. This finding feeds the "tools on another stack" check after the MVP (`MVP_scope.md`, section 10.3, `TS-35`).
  - **The design allows it.** Tools may run on any stack (`runner.md`, section 1.0 [Decided]). What every tool shares is a contract that doesn't depend on any language, and the TypeScript helper is only a convenience (`toolset.md`, section 5.5). The program is called `tool_name.bin`, standing for whatever stack the tool runs on (`toolset.md`, section 4.5).
  - **M2 is the easiest of the three tools to write in C.** It reads no source files and doesn't parse TypeScript (`TOOL-20` to `TOOL-22`). It takes JSON in and writes JSON out. Its work is matching names against exported symbols, resolving `./` and `../` relative to the importing file, and finding `<from>.ts` or `<from>/index.ts` among the files in M1's outputs without touching the disk. It copies locations as they are and never recalculates columns, so the difference between UTF-16 and byte columns doesn't matter. Use-site links (FND-03) would be just as easy.
  - **What a C version would have to do itself:**
    - the whole tool contract: `TOOL-01` to `TOOL-08`, `DATA-14` to `DATA-17`, the exit codes, and writing to a temporary file then renaming it. This is the code the TypeScript tool helper would otherwise provide, and it's the bulk of the work, more than M2's own logic;
    - reading and writing JSON, which C has no built-in support for. The least-effort rule points to an existing library rather than a hand-written parser; which one is a technology choice;
    - times in ISO 8601 UTC;
    - a C compiler and a build step in the repository (`DEL-03`).
  - **Risks:**
    - **Memory safety on untrusted input.** Symbol names and import paths come from the examined source, and a C tool that handles them carelessly can overflow buffers. This should be raised in `security.md` when this check is taken up.
    - **Checking it against the contract.** `TS-35` asks how a tool on another stack is checked, and it is still open. The test plan has no contract test that runs regardless of a tool's language.
    - **Effort.** `DEL-09`'s half day per tool for M2 and M3 assumes the TypeScript helper. In C, the contract work would probably take several times longer.
- **FND-38 Who writes a tool's store: the tool or the Runner.** Checked on 2026-11-08 against the working files. **Recommendation: tools keep writing their own stores, and the Runner owns everything about the run around them.** This changes no decision.
  - **What's already decided.**
    - Each tool writes only to its own store, and only the Runner writes the database (`toolset.md`, sections 4.2 and 5.2).
    - Every tool always writes its own log and result in its own store, and its output "to its own files, in its own folder" (section 4.1).
    - A failed invocation updates nothing in the tool's folder (`runner.md`, section 1.1).
    - Tools write only current data, with no history (`toolset.md`, section 5.3).
    - Tools are meant to be easy to replace, and meet only through the contract (section 2).

    A Runner that writes for every tool would reverse the first three and weaken the last.
  - **The trade-off:**

| | Tool writes its own store (current) | Runner writes for each tool |
|---|---|---|
| Running a tool by hand | Gives the same store, log and result the Runner and the Viewer read (B1 to B6, `last_run.json`) | Output goes to standard output and the stores aren't updated. To change what the Viewer sees, the user has to go through the Runner |
| Replaceability, any stack | The contract covers files written atomically to a folder; easy in any language | The contract shrinks to "print JSON"; simpler still |
| Dry run | Two code paths; passing results between dry runs needs extra work (`FND-04`, `RN-11`) | The tool always prints and the Runner simply doesn't write; results pass between dry runs for free |
| One consistent snapshot (`toolset.md`, section 5.3) | Each tool commits on its own, so a failure partway leaves a mix of old and new outputs (`RN-16` accepts this for the MVP) | The Runner can stage the whole run and commit it at once |
| Stale outputs, cleanup (`FND-06`) | The Runner has to delete files in stores it doesn't own | The Runner owns the files, so cleanup is natural |
| Where to write (`FND-07`) | Needs a parameter (M1's `store_path`, formerly `output_root`) | Goes away |
| Internal state (`data_topology.md`, section 4) | Lives in the same folder as the output | The tool still needs a folder for its state, so there are two writers per folder |
| A store per run | Conflicts with "only current data" either way. Per-run logs and records already exist; per-run outputs would add history that `toolset.md`, section 5.3, and `viewer.md`, section 5, exclude | Same |
| Effort in the MVP | Done: M1 does it, and 56 broken-input checks pass | Rework M1, the contract and the tests |

  - **Why the recommendation.** The Runner-writes option solves three real problems: passing results between dry runs, the consistent snapshot, and cleanup. Each of them can be solved without taking writing away from the tools. Only one property depends on tools writing their own stores: a run by hand gives exactly what the Runner gives. The design relies on that for debugging, for repeating a failed step, and for "the same data can be recreated by the user calling the Runner by hand" (`runner.md`, section 10).
  - **Who does what, as recommended:**

| Responsibility | Who |
|---|---|
| Writing its output, result, log and `last_run.json`, atomically, in its own store | Tool |
| Where the store is, passed as a parameter (`store_path`, formerly `output_root`; answers `FND-07`) | Runner |
| Whether to run: shape check, input fingerprint, skip (`RUN-17` to `RUN-22`) | Runner |
| Reading outputs, building the next tool's inputs, loading the database | Runner |
| Removing outputs that should no longer exist (deleted files, omitted tools), using only the paths in `--info` (`FND-06`) | Runner |
| The run-level log and records (`project_runs`, `project_tool_runs`) | Runner |

  - **For the product: staging without the Runner writing tool data.** The Runner points `store_path` at a staging folder for the run, and swaps it in only when every tool has succeeded. Tools still write their own stores and runs by hand still work, and the Runner gets an all-or-nothing commit. That meets "one consistent snapshot" (`toolset.md`, section 5.3) without reversing section 4.2. Out of the MVP, where `RN-16` accepts no staging.
  - **If the Runner-writes option is chosen instead,** `toolset.md`, sections 4.1, 4.2 and 4.5, must be re-decided, and a run by hand would no longer update what the Viewer shows.
