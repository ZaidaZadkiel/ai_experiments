# MVP 2: real TypeScript

> **Summary, written 2026-11-10.** MVP 2 is the MVP's **current** stage, from 2026-11-09 on; its working file is `97_second_implementation.md`. This file says what MVP 2 attempts, what it built, what it has decided, what was superseded along the way, and what is open. Nothing here decides anything; every line points to where it is recorded. MVP 1, which it builds on, is in `10_mvp1.md`.

## 1. In short

MVP 1 showed that the chain of independent tools works, but that hand-written analysis gives a wrong graph on real code. MVP 2 keeps the chain and replaces the analysis: **one new tool, `ts-program`, asks TypeScript's own compiler** what every declaration and every use is, over the whole program. **On the test source the graph is exact** and agrees with TypeScript's "go to definition" on every edge. **On real code** it is fast, but **large views can't be read**, and uses that go through packages stay unresolved because their type declarations are left out.

## 2. What it attempts

- **Goal** (decided 2026-11-09, `MVP_scope.md` 1.2): **a correct graph in the Viewer, from real TypeScript data.**
- **Rule: correctness before consistency** with the earlier work. Every part of the MVP is reconsidered and kept only where it serves a correct graph. MVP 1's least-effort rule no longer applies (`97`, section 5.1). A decision in a working file that blocks correctness is reopened there, not overridden.
- **What "correct" means** (`TSP-01`, `41_typescript_program_plan.md` 1.1, decided as the starting point): the graph shows **what TypeScript itself knows, and nothing it doesn't**:
  - every declaration is a node, once, in its lexical container, with types included;
  - every use is an edge to the declaration the checker resolves it to, statically and across files;
  - every import is a link to what it names, following re-exports;
  - what can't be resolved is listed with its reason, and built-ins are listed apart;
  - lifting edges to higher levels loses nothing and invents nothing;
  - the same source gives the same graph, byte for byte;
  - the known limits are stated: runtime dispatch, blocks, anonymous functions, type parameters, packages.
- **Test source:** the class-heavy TypeScript test from `FND-82` (`test-source-mvp2/`), later with four files in subfolders (`FND-104`). Its expected graph is written **by hand first**; writing it found six cases the definition didn't settle, added as refinements R1 to R6 (`FND-97`).
- **New claim, P5** ([Proposed], `MVP_scope.md` 7): the Viewer shows a correct graph of real TypeScript.

## 3. How it got there

1. **The plan** (`41_typescript_program_plan.md`, `FND-85`): M1 on the whole program through TypeScript's checker, with twelve decisions (`TSP-D1` to `TSP-D12`) and nine phases. Its suggested answers were written to change as little as possible, then re-examined with correctness first.
2. **The plan was overtaken** by a new tool (`42_tool_ts_program.md`, `FND-87`). M1 is kept as it is and not run. **`ts-program`** builds TypeScript's program over the listed `.ts` files, asks the checker, and writes per-file records in the existing shapes, with new keys allowed (`TPG-01` to `TPG-03`).
3. **Every pending decision was taken on 2026-11-09**, mostly as suggested, three of them changed (`FND-96`).
4. **Built, checked and measured the same day** (`FND-98`, `FND-99`), then refined in use (`FND-100` to `FND-110`).

## 6. What worked

- **A correct graph on the test source.** The tool and the hand-written graph match exactly. Where they first differed, TypeScript was right: `shapes.reduce` is `ReadonlyArray.reduce`. What the compiler knows corrected the human's expectation, as the definition intends (`FND-98`).
- **One tool was enough** (`TPG-06`, closed): nothing needed processing after `ts-program`. Links, nesting and built-ins all come from it, so M2 and M3 aren't needed (`FND-99`).
- **The contracts held for a very different tool.** The tool helper took a program tool writing many outputs without change, and the Runner needed only a run list and per-file outputs from a once tool. This is more evidence for P4 (`FND-98`).
- **Fast on real code.** On ZaAnSouVi's own `app/`, 17 files and about 6,000 lines (`FND-99`):
  - a full run takes 4.4 s, of which `ts-program` is 1.3 s;
  - an unchanged run takes 1.2 s, and a dry run 2.3 s;
  - a run through the Viewer to its graph takes 8 s;
  - the Viewer's model holds 2,992 nodes and 12,670 relations;
  - entering a 1,000-line file takes 0.2 s.
- **The Viewer reads better.** Frames with titles and notes, member lists in rows, built-ins grouped by type, the exact source text of a range (`FND-100` to `FND-110`).

## 7. What didn't work, or reached a limit

- **Large views can't be read.** One file's view on real code had 110 nodes and 349 edges: fast, but unreadable. This is **the main design problem MVP 2 found** (`FND-99`). It is the product's hard problem of readable large graphs (`toolset.md` 9), and the evidence is added to `VW-39`, which is deferred.
- **Packages leave much of the graph unresolved.** Of 12,533 uses on `app/`, 69% were resolved and 14% were built-ins; 585 went to a "package" and 1,464 stayed unresolved, almost all through Node and package modules, whose type declarations are left out of the program (`TPG-20`). This is open again as `TPG-D8`.
- **The folder structure isn't visible.** Files are drawn loose in the top view, their folders sit apart, and an edge can run under a node (`FND-104`).
- **Merged declarations show one range only**: the first overload, or the getter without the setter (`FND-106`).
- **No `ts-config` yet.** A source whose `tsconfig.json` changes how modules resolve may give a wrong graph (`FND-95`, `TPG-D4a`).
- **A running Viewer hid a server change.** Every headless check passed while the user's open Viewer showed wrong text, because the checks start a fresh server (`FND-107`). The page now checks the server's answer, and the lesson is recorded: restart the Viewer after any server change.
