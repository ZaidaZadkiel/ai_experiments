# MVP 1: the first implementation

> **Summary, written 2026-11-10.** MVP 1 is **superseded** as the MVP's working state by MVP 2 (`20_mvp2.md`) and kept as a record; its code and checks still exist and still pass. This file says what MVP 1 attempted, what it built, what it decided, and which of those decisions are still **current** or **superseded**. Nothing here decides anything; every line points to where it is recorded.

## 1. In short

From 2026-11-07 to 2026-11-09, in four sessions with AI assistance, MVP 1 built the whole chain once: three hand-written tools, a Runner, a single database and a Viewer, on a tiny test source of three files. **The chain and its contracts worked**: one command, exact outputs, tools that know nothing of each other, a Runner replaceable by a script. **The analysis did not**: on real code the hand-written tools missed classes, members and JavaScript, which is why MVP 2 rebuilt the analysis on TypeScript's own compiler.

## 2. What it attempted

- **Goal:** show that a tool-based source code visualizer can work at all (`MVP_scope.md`, section 1.1): the Runner and the Viewer work together (P1), the Runner works from one command (P2), the Viewer works as judged by a person (P3). Whether independent tools are valuable (P4) is tested after the MVP.
- **Rule:** least effort, the happy path, acceptable failures, simplicity over precision, a library or built-in wherever one does the job (`MVP_scope.md`, section 1).
- **Test source:** three small files with functions and variables only, `math.ts`, `counter.ts` and `main.ts`, with the expected result written by hand before the tools existed (`06_test_plan.md`).
- **Before building** (2026-11-06), the requirements in this folder were inferred from the working files and reviewed: about 85% of what the build needed was in place; the rest were contract gaps that would have forced the developer to guess (`99_findings.md`, `FND-01` to `FND-34`). Most were resolved before or during the build.

## 5. What worked

- **The chain, end to end.** One command runs every tool and leaves the data the Viewer needs; every output matched the hand-written expected result exactly; a dry-run-only pass reports go and writes nothing; a broken input gives a clear no-go from the right tool (`FND-51`, `FND-52`, `FND-57`).
- **Self-describing tools, with no manifest.** The Runner picked up M2, then M3, with no code change, from their `--info` alone: the first practical evidence for the no-manifest design and the generic Runner (`FND-48`, `FND-57`).
- **Independent tools.** Each tool depends on as little as possible from the others; M2 and M3 read no files, only the records they ask for (`FND-46`, decision 18 in `mvp1/99_findings_mvp1.md`, section 10.2). The Runner can be replaced by a plain script (`TEST-08`). This is early evidence for P4.
- **The tool helper.** M1 moved onto it shrank from 1,155 to 673 lines with byte-identical behavior (`FND-48`).
- **Refreshing only what changed**, brought into the MVP although its scope left it out (`FND-36`). The MVP showed that running every tool on every run is unnecessary: the same input gives the same output (`FND-52`, `FND-58`), so running a tool over and over goes against the intention. Examining a source doesn't need processing again and again; for most cases a single snapshot is enough, on the assumption that an examined source doesn't change too drastically in architecture or implementation. *This is a human judgement (the user's, 2026-11-10), not a measured result.*
- **The Viewer**, built with no tool-specific code: its own store, surviving bad data, a one-time token and strict security policy (`FND-61` to `FND-69`). Refined in use: a predictable layout, a frame for the scope being viewed, which the user judged improves readability (`FND-72`, `FND-73`), selection, zoom, grouped Problems (`FND-71`, `FND-76` to `FND-78`).

## 6. What didn't work, and why

- **Hand-written analysis doesn't survive real code.** M1 refuses JavaScript, fails on JSX, and in plain JavaScript misses classes (`FND-81`). On class-heavy TypeScript it misses classes, members, enums and namespaces, turns overloads into three functions, never records member access, and leaves 25 references unresolved; M2 then links an import as "not exported" (`FND-82`). All of this was within M1's specification ("acceptable failures"); widening M1 would have duplicated TypeScript's own binder (`FND-82`).
- **A JavaScript project gave nothing and a misleading error.** The Runner listed no files, M1 never ran, and M2's error pointed away from the cause (`FND-75`).
- **One file per invocation stood in the way.** A probe showed TypeScript's own checker works on a one-file program and keeps every rule: in `shapes.ts` it left 0 uses unresolved, where M1 left 22, and told built-ins apart with no list of globals (`FND-83`). But across files the checker needs the whole program, and a whole-program M1 collided with the one-file rule, the per-file refresh, the dry run's input-only rule and "one thing well" (`FND-84`).
- **Smaller problems:** M3's output depended on input order (fixed, `FND-58`); the layout differed on every visit, and the force layout didn't suit frames (`FND-72`, `FND-73`); nested members broke the layout, and Node's type stripping refused parameter properties (`FND-69`).

**Hence MVP 2** (`FND-85`, `FND-86`): rebuild the analysis on TypeScript's program and checker, with correctness first.
